# B-16 — RQ0: доля пользовательского кода и базовая линия R8

> **В работе, 06.09.2026.** Стенд `bench/` (три вида эндпоинтов брифа), харнесс `bench/profile/run.sh`
> с атрибуцией по происхождению кадра, базовый профиль снят по протоколу брифа. Итог по коду:
> на `/business` пользовательский код — 2,1 % CPU и 9,9 % аллокаций по владельцу (ресёрч §1.4).
> R8 с полным classpath на JDK 25 **не запускается** — member rebinding переписывает
> `invokespecial` на не-прямой суперинтерфейс (§1.3); усечённый до пользовательского jar-а R8
> убирает все 56 `Intrinsics.check*` и не меняет alloc/req ни на одном эндпоинте (§1.6).
> A/B без профайлеров, три повтора (§1.7): B/A по rps — `/echo` 1,12 (шум: там нечего менять),
> `/items` 0,99, `/business` 1,03 — внутри линейки шума. **Вердикт записан в §2, D1:** по букве
> зелёный, по механике красный для IR-слоя как продукта про производительность; решение — за
> владельцем. Сделано 06.09.2026.

Бриф: зелёный — «user ≥ 25 % аллокаций *или* дельта R8 < 3 %», красный — «user < 10 % *и* дельта
R8 ≥ 8 %». По коду порог зелёного не взят (9,9 %), порог красного — на волосок; по R8 полная
базовая линия не измерима, усечённая — ноль по аллокациям.

- **Решение — вердикт писать по механике, а не по букве.** Буква даёт «зелёный, потому что R8
  ничего не даёт»; механика — «IR-плагину есть где двигать одну десятую аллокаций и одну
  пятидесятую CPU, а всё остальное в Ktor, coroutines и stdlib». Обе записи стоят рядом в ресёрче
  §2, решение о продолжении — за владельцем (критерий остановки 1).
- Отвергнуто: заменить R8 на ProGuard ради «настоящей» базовой линии — та же классфайловая
  переписка интерфейсов, и на этом стеке никто её не применяет; базовая линия существующего
  инструмента на практике — ноль.

- AC: в ресёрче §1.7 — медианы трёх повторов A/B (baseline против R8-user-only) по трём
  эндпоинтам; §2 — вердикт RQ0 в обеих формулировках; статус этой задачи — `done`.
